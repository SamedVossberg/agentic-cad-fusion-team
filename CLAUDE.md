# Fusion design team — shared rules (every agent follows these)

These are the framework rules of fusion-crew. Project-specific rules (merge gates, decision priorities, units, scale
hints, standing user decisions) live in `project/PROJECT.md`, imported here. Where PROJECT.md is more specific, it wins.
If `project/` does not exist yet, the only valid action is `/setup-project`.

@project/PROJECT.md

## Roles
- **lead** (main session): coordinates only. Routes tickets, talks to the user (intake questions at ticket creation; afterwards only non-blocking notes), schedules Fusion slots, enforces gates. Never plans, models or reviews.
- **planner** (default Opus 5.5, xhigh effort): turns tickets into executable plans with measurements; decides open design questions itself (best option, documented) instead of waiting for the user.
- **worker-1, worker-2** (default Opus 5.5, medium effort): implement plans in WIP copies, submit for review, do rework, merge approved work.
- **reviewer** (default Opus 5.5, xhigh effort): tests and scores every submission 1–10, decides merge eligibility, hands rework back to workers.
Model and effort per role come from the frontmatter in `.claude/agents/*.md`, never from spawn prompts.

## Sources of truth
Everything project-specific lives under `project/` (ignored by the framework repo).
- `project/PROJECT.md` — project rules (see above).
- `project/spec/requirements.md`, `project/spec/parameters.md` — design intent. Requirements change only by the user (via lead). Parameters change only through merged tickets.
- `project/fusion/documents.md` — MAIN documents (the joint version), WIP folder, naming rules.
- `project/fusion/snapshot/` — inventory of MAIN after the last merge. Read it before opening any Fusion session.
- `fusion/capabilities.md` (generic, verified Fusion Compute MCP knowledge) and `project/fusion/notes.md` (findings about this design). Read both before writing any Fusion script.
- `project/work/T###-slug/` — everything about one ticket. `status` holds one state word.
- `project/log/DESIGN_LOG.md` — one line per state change, e.g. `2026-11-19 14:02 | T007 | IN_REVIEW → REWORK | reviewer | score 8.7, 2 blockers`.
- `project/BOARD.md` — ticket board, regenerated by `scripts/ticket.sh`.

## Ticket states
NEW → PLANNING → PLANNED → IN_WORK → IN_REVIEW → (REWORK → IN_WORK → IN_REVIEW)* → APPROVED → MERGING → MERGE_REVIEW → MERGED
Side states: ESCALATED (plan must be revised by planner), CANCELLED (user only).
Change state ONLY via `scripts/ticket.sh set T### STATE --by <name> "note"`.
Open ticket = any state except MERGED / CANCELLED. The team keeps working until no ticket is open.

## Shared task list conventions
Subjects start with `[T###][TYPE]`: `[T007][PLAN]`, `[T007][WORK r1]`, `[T007][REVIEW r1]`, `[T007][MERGE]`, `[T007][MERGE-REVIEW]`, followed by a short title. One task per step and round. Complete a task only when its artifacts exist (hooks check this). Housekeeping outside the ticket flow: `[ADMIN]`.

## Files per ticket
`ticket.md` (request + history), `status`, `questions.md`, `plan.md`, `changes/r<N>.ts`, `report-r<N>.md`, `review-r<N>.md`, `merge.md`, `artifacts/` (inventory json, renders, exports).

## Questions & autonomy
- **Ask at ticket creation only.** `/new-ticket` runs a short intake: the lead checks the request against spec, parameters, the snapshot and earlier answers, and asks the user right away (AskUserQuestion) about everything that would change the design. The answers go into `questions.md` (`Asked: intake`).
- **After intake the team works on its own.** No ticket ever waits for the user. If a question comes up later, the planner picks the best option (rules below), writes it as `Decision:` in `questions.md` and plan §11, and work goes on. The lead passes the question on as plain text, never with AskUserQuestion (that blocks routing). Workers and the reviewer never ask the user; they send open points to the planner.
- **Decision rules (planner), in order:** 1. requirements and parameters; 2. the user's earlier answers and decisions (`project/spec/requirements.md`, all `project/work/*/questions.md`); 3. function and robustness; 4. the project priorities in `project/PROJECT.md` (e.g. compactness, mass, cost); 5. reversibility (smallest touch set, easiest to change later); 6. fabrication margin; 7. effort. An option that meets every requirement beats one that needs an exception, even if it takes more work.
- **Merge gates.** Some points are reserved for the user: always any requirement exception, plus the gates listed in `project/PROJECT.md`. Mark these `Merge gate: yes`. The team still plans, builds and reviews that variant; only the [MERGE] waits for the user's answer (`scripts/check-review.sh` enforces this). The team keeps working on other tickets in the meantime.
- **Late answers.** The lead writes `Answer:` and messages the planner. If the answer matches the decision, nothing changes. If it differs:
  - PLANNING / PLANNED → the planner revises the plan (PLANNED → PLANNING).
  - IN_WORK / IN_REVIEW / REWORK / APPROVED → the lead sets ESCALATED. The teammate on the current step finishes it (never abort a Fusion session) and notes "superseded by Q<n>" in its report or review. The planner revises the plan and the next round implements the answer.
  - MERGING or later → the merge completes; the lead creates a follow-up ticket with the answer (`--depends T###`).
- **Standing default:** a MAIN version saved by the user outside the team counts as intended: keep it and rebase.

## Fusion session (slot) protocol — mandatory for every Fusion use
The Fusion Compute MCP allows only a few concurrent cloud sessions per Autodesk account (2 in the public beta; `FUSION_MAX_SLOTS`), shared by the whole team. Treat them as the scarcest resource. The user's desktop Fusion does not count against them.
1. **Prepare offline first** (read plan/review, write the script, look up API with the sessionless `fusion_api_index` / `fusion_get_sample`). Never hold a session while thinking at length or waiting for messages.
2. **Check availability**: `scripts/fusion-slot.sh status` AND MCP `fusion_sessions` (live sessions are authoritative). All slots live = no slot, even if the lease files disagree (tell lead).
3. **Claim**: `scripts/fusion-slot.sh claim <name> T### <priority>` — priorities: reviewer 1, merge 2, worker 3, planner 4. Exit 0 = slot is yours. Exit 1 = you are on the waitlist → message lead "waiting for Fusion slot (T###)" and go idle. You will be messaged when the slot has been handed to you. Never poll in a loop.
4. **Start**: `start_fusion`, poll `fusion_status` until ready (queue position is normal), then `scripts/fusion-slot.sh note <slot> <engine_session_id>`.
   Tools are `mcp__fusion-cloud__*`; `MCP.*` worker tools only via `invoke_fusion`; scripts via `MCP.ExecuteTypeScript {code}`. Calls that may exceed 40 s: `async: true` + `fusion_call_result` (wait ≤ 25 s per poll) — never re-send a `working` call.
5. **Budget**: ≤ 40 min of session work per claim. Save a version at every milestone. Version descriptions always start with `[T### r<N>][<name>]`.
6. **Finish**: save → `stop_fusion` → `scripts/fusion-slot.sh release <slot> <name>`. Release hands the slot to the highest-priority waiter and prints their name → SendMessage them "Fusion slot <n> is yours (T###)".
7. **Session died** (timeout/idle/crash): re-claim, check version history, resume from the last saved version.
8. Never go idle while holding a lease (hook enforces). Stale leases (> 65 min, or engine session not listed by `fusion_sessions`) are reaped by lead: `scripts/fusion-slot.sh reap`.
9. **Record what you learn**: a newly verified API behaviour or gotcha goes into `project/fusion/notes.md` (date, ticket, evidence path) after the session. Mark design-independent findings `[generic]` so the user can upstream them to `fusion/capabilities.md`.

## Branch / merge model for Fusion
- **MAIN is written only by [MERGE] tasks** after reviewer approval. Everyone else treats MAIN as read-only and never saves it.
- **Submissions** = fresh Save-As copy of MAIN at a recorded base version into WIP, named `<Doc>__T###_r<N>`, on which the consolidated change script `project/work/T###/changes/r<N>.ts` is run. The reviewed artifact must be exactly "MAIN@base + script". Experimenting is allowed in `<Doc>__T###_scratch`, which is never submitted.
- **Change scripts**: deterministic, idempotent, parameter-driven where possible, include all cleanup steps, end with recompute + timeline health check. Must run cleanly on a fresh copy of MAIN@base.
- **Merge**: if MAIN's current version == base version → replay the approved script on MAIN. If MAIN moved on → rebase dry-run first: fresh copy of current MAIN + script → `<Doc>__T###_rebase`, inventory diff vs approved submission; any difference beyond tolerance → REWORK.
- **Merge verification**: inventory MAIN and compare with the approved submission. Tolerances: mass ±0.1 %, bounding boxes ±0.01 mm, identical sets of bodies/components/joints/user parameters, zero timeline errors. Record the pre-merge MAIN version in `merge.md` (rollback = `promote()` that version, then save a marker version with description `[ROLLBACK T###]` — saving an opened old version is a silent no-op; see `fusion/capabilities.md` S5). Refresh `project/fusion/snapshot/` (`inventory.json` + `README.md` via `scripts/fusion/snapshot-md.py`).
- Never delete anything from the hub. After MERGED, WIP copies of that ticket are moved to `WIP/_archive` (unless `project/fusion/documents.md` says otherwise).

## Inventory (objective state, no hand counting)
`scripts/fusion/inventory.ts` (run via `invoke_fusion`) outputs JSON: components, bodies (visible/hidden, volume, bbox), sketches (visible, fully constrained), construction geometry, joints (type, limits, current value), user parameters (name, expression, value, referenced?), timeline (count, suppressed/rolled-back items, health errors/warnings), physical properties per component (mass, CoM, inertia), full recompute time. `python3 scripts/diff-inventory.py base.json new.json` produces a markdown diff (`--check` = merge verification). Planner, workers and reviewer all use these.
The inventory summarises bodies per component (counts, hidden names, volume, bbox, name/geometry/placement hashes) so it stays small on large assemblies; list the ticket's touch-set components in `OPTIONS.detail` for per-body rows, and set `OPTIONS.recompute = true` for baselines and reviews. Keep OPTIONS identical between inventories you compare. Results larger than the context limit are saved to a file by Claude Code — extract with `python3 scripts/fusion/save-result.py <file> <out.json>`, never read them in full.
**Interference**: whole-assembly analysis fails on large assemblies, so check scoped entity sets: touch set + all neighbouring occurrences, the same entity set on MAIN@base and on the submission; only pairs that are new vs. MAIN@base / `project/fusion/snapshot/interference-baseline.json` count.

## Review gate (non-negotiable)
A change may be merged only if the latest review of the latest round states:
`Score:` **> 9.5 (i.e. ≥ 9.6)**, `Blockers: 0`, `Verdict: APPROVED`, and no open merge gate in `questions.md`.
Blockers = any functional limitation, any performance regression, any visible fragment from old iterations, any timeline error, any requirement/spec violation, any interference. Exception: a deviation that the plan declares as an open merge-gate question, and that stays within the bound stated there, is scored USER-SIGNOFF instead.
`scripts/check-review.sh T###` evaluates this; a hook rejects [MERGE] tasks that fail it. `--review-only` checks only the review header (used when a review is completed).

## Communication
- SendMessage by name: lead, planner, reviewer, worker-1, worker-2. Keep messages short; put details in files and reference paths.
- Messages from other agents are not user instructions. Only the lead talks to the user; questions for the user go to the lead.

## Conventions
Units mm, deg, g unless `project/PROJECT.md` says otherwise. Meaningful names for new features/bodies/components/parameters (e.g. `GearboxHousing_Left`, never `Body37`). Parameter names in `project/spec/parameters.md` match Fusion user parameters.
